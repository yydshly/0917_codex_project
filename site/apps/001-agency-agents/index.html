03 / VALUE FOR US

后续按需验证的六个候选

按需求初选 · 未验证效果

依据本仓库“理解项目 → 运行验证 → 整理实践 → 展示演示”的目标，初选下列六个候选角色。它们并非官方核心名单，尚未证明更有效或全部必要；可合并为工作环节，实际效果留待深度测试。只在真实任务需要时选用，并与直接使用同一模型的结果比较。

01 / 理解源码

源码导读员

Codebase Onboarding Engineer

定位启动入口、追踪真实调用链，并逐项说明代码依据与阅读范围。

我们需要的产出
项目结构图、关键文件与数据流说明。
改造重点
保留事实约束，另设价值分析环节；原角色禁止提出改进建议。

03 / 最小验证

04 / WORKFLOW

让角色服务任务，让证据决定结论

建议用于我们的下一个研究项目

  1. 01

    固定研究问题

    记录版本、目标和判断标准，选取相关角色。

  2. 02

    导读与实验

    理解关键实现，用最小示例验证一个核心能力。

  3. 03

    核对与修正

    对照代码、日志和截图；有失败就回到实验环节。

  4. 04

    整理与展示

    写清结论、边界、复现方法与尚未验证的部分。

这是我们建议采用的研究流程，不是已经运行的自动化管线。同一会话也可按阶段使用这些角色。

先从这里开始

选取指令，按项目改写

保留任务、步骤、产出与验收要求，删除不适用的技术栈假设和角色口号。无需一次引入全部角色。

需要复用时

通过适配脚本分发

上游提供转换与安装脚本，将角色定义整理成不同 AI 工具所需的配置。转换格式本身不代表已验证兼容性。

查看转换实现 ↗

明确交接与重试

编排角色描述需求、架构、开发与测试的交接，并设置重试限制。实际调度依赖使用它的执行工具。

05 / BOUNDARIES

知道边界，才能正确使用

它提供的内容仍需我们完成的部分
专业角色与领域指令帮助组织模型已有能力提供准确上下文，核验事实；角色名称不代表真实专家资质。
协作流程与交付标准定义顺序、交接与检查点接入执行工具、管理状态与权限；文本中的“记忆”不是持久化实现。
质量检查与证据要求鼓励对照实际结果选择合适证据；截图不能单独证明接口正确、安全性或性能。
多个领域与工具的覆盖方便选取和迁移角色逐项测试适配性；角色数量与覆盖范围不代表质量评分。
需要改写的具体规则

部分测试角色预设必须发现问题，并引用固定的 Laravel 路径和截图脚本。借鉴其证据意识，按项目替换命令、验收条件和不必要的重试。

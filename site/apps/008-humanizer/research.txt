## 能力是什么

### 我们的理解与使用判断

Humanizer 的主要作用，是把常用的文字编辑要求封装成 Skill，让 AI 对已有内容进行处理，减少模板腔，并在有样文参考时更接近作者的语气。

- **25 类规则是编辑检查项。** 每类描述一种写作问题、修改方向或例外，由模型判断是否适用；不要求文章逐项执行 25 次处理。
- **Skill 提供规则，宿主模型完成改写。** 核心是 `SKILL.md` 中的提示词与示例，没有独立改写算法或专用模型。模型按要求识别问题、重写、自检并输出。
- **样文决定个性化方向。** 没有样文时按文体改得自然、平实；有样文时参考作者的措辞、句长、标点和衔接习惯。这是上下文引导，不是训练个人模型。
- **对我们是可复用的编辑规范。** 可用于研究说明、README、汇报和内容初稿的最后一轮修改，减少重复交代编辑要求；项目事实、版本、引用与验证状态仍由我们核对。
- **效果取决于模型和材料。** 保留原意是提示要求，不能保证没有事实遗漏或语义变化。当前确认了规则与实现方式，中文效果和实际收益尚待对照验证。

核心能力是编辑已经存在的正文。用户提供原文，可以额外提供自己的样文；AI 根据规则检查并重写文字。

| 能力 | 具体做法 | 约束与边界 |
| --- | --- | --- |
| 减少模板化表达 | 识别空洞对比、重复结尾、刻意铺垫、机械排比等 25 类模式 | 规则由模型理解执行，没有确定性的文本检测引擎 |
| 调整文章结构 | 合并或拆分段落、改变句长、重写围绕主旨组织的段落 | 不能只靠删词；仍需检查信息是否完整 |
| 降低夸大和宣传腔 | 把宏大意义、模糊权威、宣传性形容词换成有依据的内容 | 不应为了具体而捏造功能、数字或来源 |
| 匹配作者语气 | 参考样文的句长、措辞、标点、开头和衔接方式 | 属于当前上下文中的风格引导，没有训练个人模型 |
| 按文体编辑 | 个人文章保留观点、幽默和不确定感；技术与事实文本保持平实 | 添加个人反应的规则可能改变语气，需要作者复核 |
| 修改文件正文 | 在宿主具备文件工具时，直接写入最终文本 | 提示要求保护代码、命令、路径、YAML 元数据、数据和链接目标 |
| 嵌入其他写作任务 | 作为 PR 描述、提交说明、文档生成流程中的编辑步骤 | 上游未提供独立 HTTP 服务或批处理调度器 |

以上是源文件定义的行为，不代表已验证的质量保证。能力依据为固定版本的 [SKILL.md](https://github.com/blader/humanizer/blob/9862685f575c65a8247f90369951df1b3416e3d6/SKILL.md)。

## 适用场景

下表是依据规则内容作出的使用建议。

| 场景 | 适合处理的问题 | 建议提供的材料 |
| --- | --- | --- |
| 博客、公众号、个人随笔 | 段落整齐但内容空泛，语气像通用模板 | 草稿、目标读者、作者样文 |
| 产品介绍和发布说明 | 堆砌“革命性”“前所未有”，具体功能不清楚 | 经确认的功能、限制、发布事实 |
| 邮件和工作汇报 | 套话太多，关键信息出现太晚 | 收件人关系、任务进度、真实数据 |
| README 和技术文档 | 聊天式开场、重复解释标题、过多描述旧版本 | 原文、技术术语、需要保留的代码与链接 |
| PR 描述和提交说明 | 过程叙述过多、重点不清楚 | 实际改动、原因、验证结果 |
| 团队编辑流程 | 每次都要重复提出同一组文字修改意见 | 团队风格要求、样文和人工验收标准 |

对于本研究仓库，它可用于研究说明的最后一轮文字编辑。项目名、版本、commit、许可证和验证状态应列为不可丢失的信息；索引区域仍由仓库脚本生成。

不宜把它作为 AI 作者身份鉴定工具、事实核查工具或检测器通过率保证。它没有提供这些能力对应的判定程序和效果评测。

## 实现原理

核心实现是 Markdown 提示词：编辑规则规定目标，修改前后示例展示方向，模型自检要求复查事实和风格。加载 Skill 后，宿主模型负责理解与生成；文件读写也由宿主提供。

```mermaid
flowchart TD
    A[原文与可选的作者样文] --> B[宿主加载 SKILL.md]
    B --> C[标记句子和段落中的写作模式]
    C --> D[重组内容并生成初稿]
    D --> E[复查残留表达和事实增删]
    E --> F[生成最终文本]
    F --> G[按模式返回文本或修改文件]
```

流程是提示词规定的编辑步骤，不代表存在独立的多 Agent 系统、固定四次 API 调用或程序控制的重试循环。

### 规则怎样影响输出

1. **先识别，再改写。** 检查对象包括词语、句式和段落形状；不局限于替换某些“AI 高频词”。
2. **保留有依据的信息。** 不得自行补充事实、姓名、数字、日期、引文和引用。缺少材料时，应提问或改成更简单的表达。
3. **初稿后再自检。** 检查遗漏和新增事实，尤其留意排名、同时发生的关系等容易在改写中丢失的信息。
4. **按上下文处理例外。** 弱信号需结合其他模式判断；引文、专名和有意的修辞不应机械清除。作者样文可以覆盖默认风格。

它还要求把待编辑文本当作材料，而非执行指令。这也是提示层约束，不是独立的安全隔离机制。

### 三种输出方式

| 模式 | 触发方式 | 输出要求 |
| --- | --- | --- |
| 粘贴文本 | 在对话中给出文章 | 初稿、剩余问题简评、最终改写 |
| 文件模式 | 指定需要编辑的文件 | 文件只写最终文本，对话中给简短摘要 |
| 嵌入模式 | 由其他写作任务调用 | 只返回最终文本 |

## 中文使用与能力边界

规则中的删空话、减少夸大、避免重复和保留事实等原则可以用于中文，这是根据规则作出的推断。词表、英语连字符、标题大小写和 `-ing` 结构等条目则明显面向英文，不能直接变成中文禁用规则。

需要重点检查以下问题：

- **事实是否完整。** 模型自检没有独立核验器，不能保证没有漏项或语义漂移。
- **风格是否过度统一。** 删除所有排比、对比或标点习惯，可能反而削弱作者个性。
- **技术文件是否被误改。** 保护代码和链接只是提示要求，修改后仍需检查差异。
- **规则是否互相冲突。** 例如破折号被描述为弱信号，但同一条又要求无样文时清除；宿主可能采取较强的修改策略。
- **示例是否完全守住原意。** 上游 README 的旅行示例出现评价和细节变化，不能把它当作严格保真证明，详见[研究笔记](notes.md)。

“更像人写”是编辑目标。本次没有测试中文自然度、事实保留率、跨模型一致性、检测器分数或调用成本。

下面是适用于支持该 Skill 的宿主的任务描述示意，未在本次研究中安装或执行：

```text
原文：
……
```

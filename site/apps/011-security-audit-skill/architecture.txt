# 实现原理与证据边界

研究基准：`c1c8a8c1471069fb0e188eeaff69b8e8db6564a8`。源码入口见 [sources.md](sources.md)。

## 三层分工

| 层 | 仓库提供 | 实际执行者 |
| --- | --- | --- |
| 方法与编排约定 | SKILL.md、侦察/调查/验证指令、攻击类别 | 主代理读取规则，调用宿主的子代理工具组织工作 |
| 判断与本地验证 | 证据门槛、最小复现方法和执行边界 | 子代理读取目标源码，必要时在宿主提供的沙箱中运行测试 |
| 数据校验 | report-schema.json、两个 .cjs 校验器 | Node.js 检查数据结构与部分语义约束 |

仓库没有附带完整的模型服务、独立调度服务或通用沙箱运行平台；这些是使用流程的外部前提。Markdown 中的执行要求不能自动变成操作系统隔离。

## 六阶段的数据流

| 阶段 | 角色与动作 | 产出 / 状态 |
| --- | --- | --- |
| 1 侦察 | 四个基础侦察角色分别检查产品技术栈、权限控制、输入与 sink、本地执行与部署可见性；必要时增加专项角色 | 主代理形成 architecture.md 和初始 coverage-ledger.json |
| 2 调查 | 主代理分配覆盖单元；调查者沿源码路径深入，返回结构化检查、候选和遗漏 | 主代理更新覆盖记录；覆盖检查代理提出补查任务 |
| 3 验证 | 按 fingerprint 和根因去重，每个候选交由新的验证者重读源码并尝试反驳 | confirmed / needs_validation / rejected 记录 |
| 4 记录 | 主代理按 fingerprint 排序，写 findings.json，运行两种校验 | 合规的最终候选记录与覆盖记录 |
| 5 复核 | 新代理检查最终记录，重大根因、结果、等级或结论改变再交独立代理复核 | 已复核记录，或记录未完成原因 |
| 6 报告 | 从已复核 JSON 与覆盖记录派生文字，不能在文字中提高影响或改变结论 | REPORT.md、FINDINGS-DETAIL.md、NEEDS-VALIDATION.md |

`FINDINGS-DETAIL.md` 包含已确认 medium / high / critical 记录的完整路径与本地复现。被排除的记录留在 JSON 中用于后续去重，不作为漏洞展示。

## 覆盖记录的确定性

单元以“入口 × 信任边界 × 子系统 × 攻击类别”组合定义。深度模式还可拆生命周期；快速模式使用固定的粗粒度子系统身份。

每个维度保留显示名称和稳定源码引用。引用经过 Unicode NFC 合法性检查与 RFC 3986 百分号编码，再以 `::` 连接为 `coverage_id`。行号、代理、轮次和结论不进入 ID，避免普通代码移动或改名造成无意义的身份漂移。按 ID 排序，重复或语义冲突必须报错。

状态包括 planned、in_progress、blocked、covered、candidate、not_applicable、out_of_scope、deferred。已覆盖或候选状态需要具体读过的路径与检查证据；未分配和延期状态不能冒充完成。每条检查有自己的代理所有者，单元路径列表必须等于各检查路径的并集。

覆盖检查代理每轮寻找遗漏入口、平行路径、生命周期和没有证据的关闭项。standard / deep 除每轮检查外，还要求独立的最终检查；quick 仅一轮调查与一次最终覆盖检查，新发现任务标为 deferred。

这里的“确定性”是单元身份、排序和记录规则，漏洞探索与模型判断本身仍有不确定性。

## 跨轮记忆与预算

复用既有记录前，必须对照当前相关源码和成立条件；不能只看 commit 标签。相同根因保持 fingerprint；改变的源码、待验证和未覆盖内容进入当前工作。旧 confirmed 也要走本轮验证，不直接继承结论。

预算按代理调用次数计算，先为侦察、覆盖检查和候选验证预留次数，再分配调查。若连必要阶段都无法容纳，流程不应启动一轮虚假的完整审计；若后续验证预算不足，记录 incomplete 和具体未验证单元。

## 校验器具体做什么

`validate-findings.cjs` 是针对本仓库使用的 JSON Schema 关键字实现的零依赖解释器，不是通用漏洞扫描引擎。额外检查包含唯一 fingerprint、安全相对路径、trace 首尾顺序、非空可见文本、结论与字段互斥、overall severity 不高于记录中的 impact。

`validate-coverage-ledger.cjs` 检查规范化 ID、排序、重复与语义冲突、状态字段约束、检查所有者、路径并集、历史 attempts、工件引用的归属形状等。脚本还限制输入体积、嵌套深度和错误输出，避免无限量处理。

两个命令行入口读取的是 JSON 记录，不是目标仓库源码。路径字符串合法不等于对应源码真实存在；声明“观察到结果”不等于脚本重新复现了结果。这些事实仍需独立代理核对。

## 执行与证据留存

上游要求操作系统强制隔离：禁止外网、空环境加显式白名单、只读目标和工具、只在分配的 scratch 中写入、限制 CPU/内存/进程/文件/磁盘/时间。它还规定由可信主代理侧代码通过不跟随链接的描述符操作，把白名单内的普通文件提升到只读证据区域，避免直接信任目标程序生成的文件。

这些流程约定不等于该仓库已经实现全部平台适配。源码还要求校验器读取 JSON 时支持 no-follow 与 nonblocking 输入保护；跨平台运行需要核对实际能力，本次没有进行上游运行兼容性测试。

## 假设教学案例

某接口允许已登录用户根据 ID 获取记录，调查者怀疑遗漏租户绑定。

- 如果本地虚拟用户确实取得另一虚拟租户记录，完整路径没有防护阻断，经过独立验证可成为 confirmed。
- 如果是否隔离取决于源码不可见的数据库策略，应保留 needs_validation，并要求确认具体策略与当前身份。
- 如果重读源码发现必经中间件已验证所有权且能阻断路径，候选应为 rejected。

交互页只切换预先编写的这三种证据条件，不扫描代码、不调用模型、不执行请求。

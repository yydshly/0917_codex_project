function applyDateFilter() {
  const selected = dateInput.value;
  let visible = 0;
  for (const row of taskRows) {
    row.hidden = Boolean(selected && row.dataset.due !== selected);
    if (!row.hidden) visible += 1;
  }
  count.textContent = `共 ${visible} 项任务`;
  emptyState.hidden = visible !== 0;
}

日期是日历日期字符串，直接比较，无需先转换成跨时区时间戳。

如果需求变复杂，还能坚持用这个方案吗？＋

如果需要跨时区预约、禁用不连续日期、复杂区间选择或指定日历交互，应重新核对原生控件是否足够。缺少明确功能时，就继续评估已有依赖或编写必要实现，不能因为“代码少”就省略需求。

SKILL.md 的内部结构

不只是“写短一点”。

它把触发条件、判断顺序、禁止事项和例外写在一起，持续提醒模型如何取舍。

阅读完整 Skill ↗
01元数据：什么时候加载？

name 标识技能，description 描述编程、重构、修复、选库等触发场景，也排除一般知识和翻译等非编程任务。元数据帮助宿主发现与选择技能；实际激活还取决于宿主。

02角色与持续性：保持什么倾向？

设定“高效但不草率的资深开发者”角色，并要求模式持续生效直到关闭或会话结束。这是文本层面的行为提醒，不是改变模型权重。

03决策阶梯：先选哪条路？

按“必要性 → 仓库复用 → 标准库 → 平台原生 → 已安装依赖 → 简短实现 → 必要新代码”的顺序检查。在理解代码和需求后，停在第一个满足要求的方案。

04工程规则：什么不该新增？

避免未经请求的抽象、未来脚手架和无用配置；修复前搜索调用方，把修复放在共享根因处。对已知有上限的简化留下 ponytail: 注释，写明限制和升级条件。

05输出约定：怎样交付？

默认代码优先，简要说明省略了什么、何时需要补上。用户明确要求的报告和详细解释应完整提供；非平凡逻辑要留下可运行检查，不能覆盖项目已有的测试约定。

06例外边界：什么不能省？

不能为缩短代码删掉明确需求、信任边界校验、防止数据丢失的错误处理、安全措施和基本无障碍；也不能省掉理解真实调用流程的步骤。

它的“约束”，强到什么程度？

代码执行的部分

模式与文本处理

解析模式参数、读取配置、筛选文本、保存状态、输出宿主所需格式。这些可以通过确定性测试核对。

模型遵循的部分

工程判断与行动

是否读全调用链、复用是否合适、是否过度抽象、能否保留所有边界，由模型结合任务判断。

交付仍需验证的部分

功能与实际收益

提示词没有自动阻断违规代码。依然需要测试和审查；代码更少也不自动等于质量更好。

理解它的价值，也理解它的边界

把“先复用，再实现”
变成 AI 的开发习惯。

核心价值是减少不必要的工程工作。实际增益取决于模型原本的能力、需求复杂度，以及已有项目规则是否已经覆盖这些原则。

实现之后，还有三种检查入口。

ponytail-review
检查当前改动中的不必要复杂度；只给建议。
ponytail-audit
扩展到全仓库，寻找可删除或替换的实现。
ponytail-debt
汇总 ponytail: 注释中的局限和升级条件。

这些复杂度检查不能替代正确性与安全审查。

PONYTAIL

先理解，先复用，再写必要的新代码。

读图顺序：看价值 → 分清接入路径 → 理解模型决策 → 用案例核对 → 识别约束边界

01

它的作用：减少重复实现与过度设计

核心是工程规则 Skill；读代码、改代码和运行检查，仍由宿主 AI 助手完成。

开发前 / ponytail

先找已有能力

复用项目代码、标准库、原生功能与已有依赖，缺什么再补什么。

审查 / review · audit

找出可删的复杂度

检查当前改动或整个仓库，给出删除与替代建议；默认不应用修改。

跟踪 / debt

把刻意简化留下记录

汇总 ponytail: 注释中的局限与升级条件；未标记的债务不会自动出现。

辅助入口：gain 展示历史评测，help 提供帮助。它们不实时测量当前项目的质量或节省量。

02

整体构成：一套原则，多条送达路径

插件是打包与注册机制，可同时包含 Skill 和 Hooks；规则文件与 MCP 是另外的接入方式。

A  按需调用

Skill

宿主发现 name / description
用户调用或宿主按任务选择
加载 SKILL.md 正文

B  自动激活

插件 + Hooks

插件登记技能与事件脚本
事件触发 → 读取模式与 Skill
构建规则 → 输出宿主上下文

C  静态约定

规则文件

AGENTS.md / 宿主规则目录
保存核心原则的紧凑版本
由宿主按自己的约定读取

D  协议取用

MCP

请求 Prompt 或规则工具
共用构建器 → 返回规则文本
由宿主提供给模型

汇合点：宿主的模型上下文

Ponytail 规则 + 用户需求 + 项目约定 + 已读取的代码与工具结果

不必全部安装或叠加。规则内容相通，但加载时机、模式管理与子代理支持随宿主而异。

03

技术原理：程序送达规则，模型完成判断

以下为插件 + Hooks 路径；只调用 Skill 或读取静态规则时，不必经过同一套 Node.js 脚本。

1  读取配置

环境变量 → 配置文件 → full
写入当前模式状态

2  构建正文

读取 Skill，去掉文件头
筛选当前强度示例，保留边界

3  宿主接收

Hook 输出文本或宿主 JSON
宿主识别后加入上下文

4  模型行动

用原有搜索、编辑、终端工具
阅读代码 → 选择 → 实现与验证

04

一个场景：给研究任务清单增加日期筛选

同一需求，根据已有能力选不同路径；这是教学示例，不是启用前后的模型对照结果。

需求

按所选日期筛选任务。
清空后恢复全部列表。

项目已有合适的 DateFilter

停在第 2 步：复用组件，接入现有列表。

没有日期组件，但原生控件满足需求

停在第 4 步：日期输入框 + 现有过滤逻辑。

交付完整需求

日期输入 · 清空 · 数量 · 空状态
避免重复造组件或新增日历库
复杂需求出现时，重新判断方案

05

约束边界：少写代码，不能少做必要的事

明确需求、安全、输入校验、数据保护、无障碍，以及必要的可运行检查，都不能因精简被省略。

程序层面 / 可确定性检查

模式、文本与送达机制

配置解析、状态文件、规则过滤、输出格式可以测试；这些检查不等于验证模型的开发质量。

模型层面 / 需要验收

工程判断仍是软约束

是否读全代码、正确复用、保留边界，由模型执行；共用 Hooks 不会审核每次补丁并阻止违规写入。

本研究证据

源码核查 + 3 项 MCP 指令测试 + 7 步隔离 Hook 验证；没有运行真实宿主中的模型开发对照。

验证观察：普通请求不一定重发规则；切换模式不等于重载全文；off 不会删除已有对话上下文。

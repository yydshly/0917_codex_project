# 讨论整理：审计什么、怎样约束、得到什么

## 我们最终形成的理解

**这个库指导 AI 从业务逻辑、身份权限、输入与接口、数据流以及底层环境等角度，对代码和业务实现的安全质量进行系统性检查。**

这里的“代码业务质量把控”限定在安全维度：是否允许不该发生的操作，是否突破权限、数据或资源边界。它不等同于完整的功能正确性、可读性、性能或可维护性评估，也不提供登录、权限或防火墙组件。

能力的起点是用户交给它的目标源码和审计范围。Skill 提供调查方法和执行规则，宿主 AI 读取代码、调用工具、分配子代理并判断证据。

## 从哪些角度检查

| 角度 | 核心问题 | 例子 |
| --- | --- | --- |
| 业务逻辑与生命周期 | 状态转换、顺序和恢复是否破坏安全约束 | 重复退款、并发核销、撤销权限后仍可操作 |
| 身份、权限与隔离 | 谁能做什么，能操作谁的资源 | 未登录访问、普通用户执行管理员动作、跨租户读写 |
| 输入、接口与敏感操作 | 输入的范围、类型与用途是否始终受到正确约束 | 文件路径越界、查询或命令注入、参数改变实际权限 |
| 数据与秘密 | 数据复制、缓存、导出、删除后是否仍正确隔离 | 他人数据出现在缓存、密钥暴露、恢复已撤销数据 |
| 组件、协议与平台 | 组件之间对身份、数据和能力的理解是否一致 | 浏览器消息、RPC 重放、AI 工具动作与批准内容不一致 |
| 底层、部署与供应链 | 内存、资源、发布权限与运行配置是否产生边界失败 | 越界写、共享资源耗尽、CI 发布权限扩大 |

外部入口不只 HTTP API，还包括文件、消息队列、命令行参数、环境配置、插件、模型上下文和本地 IPC。检查对象按源码中的实际边界选择，而不是把所有规则机械套一遍。

## 怎样从入口梳理

**谁进入 → 能输入或操作什么 → 经过哪些认证、授权与转换 → 最终触达什么资源 → 哪条边界可能失效 → 是否有具体证据。**

调查还要读取同一效果的批量、旧版、异常、重试、并发、撤销、迁移和恢复路径。输入最初合法，也可能在缓存、二次解释或后续授权中出问题。

以假设的订单接口为例：用户 A 输入订单 ID，接口检查登录，再查询并返回订单。模型要继续核对查询、必经中间件和数据库策略是否绑定订单归属。局部看不到检查并不代表全路径没有控制；若关键策略在源码之外，应明确保留待验证事实。

## Skill 的七类约束

| 约束 | 具体要求 | 如何落实 |
| --- | --- | --- |
| 目标 | 写清低信任主体、输入或动作、边界、资源与结果 | 主代理和调查提示要求以安全不变量提出候选 |
| 路径 | 从入口追到最终效果，并核对最强可见控制和其他路径 | 调查者读源码，独立验证者重新核查 |
| 覆盖 | 每个检查单元保留路径、负责人、检查与未决项 | coverage-ledger + 覆盖检查代理；脚本检查状态和字段规则 |
| 证据 | 已确认必须有完整路径、成立条件和受限本地观察 | 验证者核实；关键事实不足记 needs_validation，无严重性 |
| 独立性 | 发现者不能自行完成独立验证，重大改写还需新复核 | 主代理使用宿主子代理工具分工；并非校验器自动证明独立性 |
| 执行 | 仅受限本地验证，断外网、隔离写入、白名单环境和资源上限 | 宿主与操作系统沙箱强制实施；缺条件时不得执行相应目标代码 |
| 输出 | 三种结论字段分开，报告忠于最终记录，披露范围与遗漏 | JSON Schema + Node.js 校验器；事实真实性仍靠证据复核 |

### 三种机制的强制程度不同

1. **指令约束：**Markdown 被主代理读取，相关规则进入子代理提示；实际遵守取决于模型和协调过程，可能遗漏或误解。
2. **程序检查：**脚本对明确的数据规则报错，如待验证记录带严重性、覆盖状态缺证据字段。它不理解目标源码，也不会证明一次复现真的发生。
3. **环境隔离：**文件权限、网络隔离和资源限制由操作系统实现。Skill 规定前提，但没有附带完整跨平台运行与隔离系统。

## 完成后得到什么

执行流程是“侦察 → 调查 → 候选验证 → 结构化记录 → 最终复核 → 报告”。quick 合并候选验证与最终复核，但仍保留独立于发现者的验证，并明确部分覆盖。

| 产出 | 使用者得到的结果 |
| --- | --- |
| 已确认 | 问题位置、完整路径、成立条件、最小本地复现、已证明的影响、严重性和修复建议 |
| 待验证 | 源码支持的疑点、具体缺失事实、受限本地或维护者观察的验证计划；不赋予严重性 |
| 已排除 | 被有效控制或反证推翻的候选及理由，保留记录避免重复误报 |
| 覆盖说明 | 查了什么、没查什么、什么被阻碍、旧发现如何复核，供下一轮继续 |

预期价值是让审计更可追踪、可复核，减少无证据猜测和重复调查。**本研究没有测量真实检出率、误报率或成本；独立代理也可能共同漏判。** 完成报告和通过校验不能证明系统完全安全，流程也不直接修改目标代码。

## 与 9 月 15 日研究的 Defending Code 对比

前次研究的是 [Defending Code 研究页](https://yydshly.github.io/0915_codex_project/008-defending-code-harness/)，上游 `anthropics/defending-code-reference-harness`，固定版本 `d3bea6b5793b5f3d59a75ebe69a58efa88383145`。当时也讨论过“是不是按规则检查代码质量”；其核心同样是漏洞研究，不是通用质量评分。

| 维度 | Security Audit Skill / 本次 | Defending Code / 先前研究 |
| --- | --- | --- |
| 共同方法 | 模型读代码、形成假设、最小验证、独立复核、保留证据 | 同样采用假设、输入实验与独立复现 |
| 形态 | Skill 方法与审计流程 + JSON 校验程序 | Skill + Python 可执行漏洞研究框架 |
| 默认范围 | 业务、权限、数据、AI、协议、部署、内存等边界 | 自动流水线默认 C/C++ 内存漏洞；也有静态审查入口 |
| 执行依赖 | 宿主提供模型、子代理、工具与沙箱 | 现成调用层绑定 Claude Code，使用 Docker / gVisor / ASAN |
| 主要工程重点 | 确定性覆盖记录、证据门槛、最终结论与报告一致性 | 构建目标、构造输入、独立容器复现、恢复与补丁验收 |
| 修复 | 提供最小修复建议，审计流程不改源码 | 独立 Patch 命令生成候选补丁并分层验证，仍需审查 |
| 适配 | 选择真实边界对应的领域方法；核对宿主执行条件 | 其他语言或模型需调整调用、构建、输入和检测信号 |
| 已知限制 | 指令和校验不保证事实正确或发现全部问题 | 工具执行与检测信号也不等于完整安全证明 |

上表比较的是已研究版本的能力与机制，没有做两者同目标、同模型、同预算的效果对照，不能得出谁检出更多或更准确。

### 与其他研究的定位关系

- **Ponytail：**关注代码是否必要、是否重复、是否过度设计，优先复用已有能力。
- **Impeccable：**关注页面设计与体验质量，配套检测器直接检查部分界面问题。
- **gstack：**覆盖需求、开发、审查、测试和交付等研发环节，并非专门只做安全审计。
- **Security Audit Skill 与 Defending Code：**聚焦安全边界与漏洞证据；前者在审计覆盖和记录规则上细化，后者提供更多目标运行与候选补丁验证实现。

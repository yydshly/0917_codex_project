# 后续：用真实产品任务验证效果

状态：**待开展**。已有内容账号案例只证明流程可以接力、保存产物和定点返工；不能证明产品质量提升、角色必要性或净节省时间。

## 当前理解

001 / 002 主要提供角色身份、专业方法和交付要求。003 提供选角色、拆任务、按依赖执行、传递结果、记录产物和反馈续跑能力。它加载所配置的角色包版本，不自动读取我们研究仓库中的角色快照。角色可由同一模型或不同模型扮演。

质量控制已有 `assert`、`acceptance` 和返工，但完整性、事实准确性、最终阻断策略仍需设计。重复执行可以通过续跑减少；对于重复内容、角色冗余和协作增益，我们尚未发现能普遍自动判断并优化的机制。

## 选择一个真实产品任务

从我们实际需要推进的产品中，选择一个范围明确、能够验收的小功能，例如需求澄清、交互方案、实现计划与测试清单。产品与功能尚未选定，不用虚构产品成果代替试验。

给三组方案完全相同的材料：真实需求、已有代码或接口说明、目标用户、必要证据、禁止事项、交付格式和验收清单。对比：

| 方案 | 做法 | 想回答的问题 |
| --- | --- | --- |
| 单次生成基线 | 使用认真设计的单次提示词，由同一基础模型完成任务 | 不增加编排时，模型已经能做到什么 |
| 精简工作流 | 2—3 个职责清晰的角色，分工和输出直接对应验收项 | 少量分工能否增加有效贡献 |
| 较完整工作流 | 更多角色参与相同任务，但不额外提供资料 | 新增角色是否有独立价值，还是增加重复与约束遗漏 |

尽量固定模型版本和生成设置，记录实际调用、材料、耗时及人工修订。对多个真实任务重复试验，避免凭一次好结果下结论；不能对齐的条件单独注明。

## 检查什么

| 维度 | 记录方法 |
| --- | --- |
| 交付质量 | 对照事先定义的验收项，记录遗漏、错误、不可执行内容和最终通过情况 |
| 事实与来源 | 重要结论是否有来源；代码、接口和用户信息是否被编造或误解 |
| 约束保留 | 原始硬约束有没有传到所有相关步骤；反馈后有没有再次丢失 |
| 重复与必要性 | 标记各角色独立贡献、重复段落、冲突意见和可删除步骤；移除角色后重新比较 |
| 人工成本 | 阅读、核验、修订和返工用时；不能只比较模型生成时间 |
| 运行成本 | 端到端耗时、调用次数、可获得的完整用量；缺失用量不冒充实际账单 |
| 产品效果 | 方案是否在产品中落实，是否通过实际测试；有真实用户试用时记录反馈 |

## 交付前的独立关卡

客观规则交给程序核对，内容问题由模型辅助审查，事实和可用性独立验证；所有关键项通过才交付。对审批明确配置拒绝分支；在最终产物上重新做结构检查，避免 `acceptance` 返工后破坏先前 `assert` 的结果。

AO 输出代码或方案后，仍需在产品环境中实现、运行测试和验收，不将“写出了文件”计为“功能已经实现”。发布与业务操作按实际授权单独执行。

## 决策方式

如果工作流在多次同条件试验中改善质量或减少人工总成本，再将它沉淀为模板；如果额外角色只增加篇幅、调用或重复，就精简角色和步骤。先记录证据，再判断是否值得用于我们的产品开发和研究流程。
